# OART: команды рисования и диаграммы Office12

18 октября 2026 года. Статическое исследование **REA + Ghidra 12.1.4**; PowerPoint и функции DLL не запускались. Исследован установленный Windows x86 `C:\Program Files (x86)\Microsoft Office\Office12\OART.DLL`, версия `12.0.4518.1014`, SHA-256 `1f739ee0f05dd8a902febe4ea19da2f535567b36e6f8fd55befbefb120341fa2`, 14 151 456 байт. Это не исследование Microsoft 365 или macOS-движка.

## Завершённый проход и сохранение

Стандартный автоанализ занял **428,595 секунды** и завершился: база `0x3a9d0000`, **88 331 процедура**, **7 141 определённая строка**, 6 блоков памяти. Обзор: `research/oart-analysis/overview.json`, Evidence `ev_f2079ab67f455e9c9d1acab6b43f70419e0d9fb40012c38f83f590c4a0b4f5d2`. Эти числа отражают определения Ghidra, а не доказанную полноту исходного кода.

Скрипт `scripts/research-oart.cjs` использует одну непрерывную публичную MCP-сессию через `scripts/rea-session-client.cjs`, таймаут старта 30 минут и heap 3 ГБ. Переменные окружения заданы только дочернему процессу; бинарник Office не изменён. Адаптивные запросы сохранены в `research/oart-analysis/queue.json`; каждый пакет экспортирует `evidence-bundle.json`, завершение сохраняет `analysis-snapshot.json`. Snapshot содержит результаты REA, не нативный проект Ghidra.

`function-index.json` индексирует **34 успешных dossiers для 31 уникальной процедуры**; повторные адреса возникают из-за нескольких ссылок внутрь одного несмежного тела. Для уникальных процедур сохранены отдельные `0x….pseudocode.c` и `0x….assembly.txt`. Неуспешные запросы остаются отдельными JSON, без подмены успехом.

После завершения проверены JSON-экспорт и snapshot: **60 Evidence records** в каждом, все 34 dossier Evidence ID присутствуют в bundle. Размер bundle — 19 374 597 байт, snapshot — 37 822 562 байта. `close_binary` успешно завершён, runner вышел с кодом 0.

## Условия доступности: что наблюдено и что выведено

Значения таблиц методов прочитаны `read_bytes`, по 48 байт (`vtable-*.json`). В слотах `+8` Align/Distribute/Group/Ungroup находятся процедуры, которые вычисляют биты состояния. Семантика «доступность команды» является **выводом по роли таблицы, ветвям и записи флагов**; запуска UI не было.

- **Align, `0x3aa8236c`**: после общих проверок при байте объекта `this+0x30 == 0` условие использует `field >= 2`; при другом значении байта — `field != 0`. Evidence `ev_9927e574709760811a4b9f790cc422458207314d56c29daa2c004da59ea26a53`.
- **Distribute, `0x3aa82c20`**: аналогичная структура, но порог **3** вместо 2. Evidence `ev_5239d2a55c90d30d406be6bec9335884e1b29264dda56fc07bcdc482560b898a`.
- Общий helper `0x3b23f31a` получает объект с RTTI `.?AVDrawingSelectionInfo@Dr@@` и возвращает его поле `+8`, либо 0 при отсутствии объекта. Интерпретация этого поля как числа выделенных элементов — обоснованный **вывод**, не восстановленное имя поля. RTTI подтверждён отдельно байтами `selection-type-bytes.json` и поиском `selection-strings.json`. Evidence helper `ev_40d507c6230c89bc6a20d573a6a570329412d17a845e57340622f94d86b3a274`, строки `ev_55a51c3eb5302025a6e50e0d9dc008a927e782942b7d7b4f80b7e9b506af94e9`.
- **Group, `0x3aa82df8`**: присутствие DrawingSelectionInfo, значение другого helper `>1`, затем цикл с дополнительными проверками каждого элемента. Одного количества недостаточно. Evidence `ev_45c367a1469e375b4a5814a7a942adbc4840492f953c42bce83e95686b3de8fd`.
- **Ungroup, `0x3aa834ac`**: строит коллекцию, проверяет элементы и требует хотя бы один подходящий объект; проверяет поле `+0x8c` и байт вложенного объекта `+5`. Имена/точная семантика защитного флага неизвестны. Evidence `ev_2673272f30bf6a6358a42e58debee0621f48b6ac4237ce85dcb1c997ba591e34`.

Байт `this+0x30` может описывать альтернативную область выравнивания, но **привязка к «относительно слайда»/«относительно выделения» не доказана**. Нельзя переносить эту гипотезу в документацию как факт Ghidra.

В слотах `+4` Group/Ungroup доступны большие процедуры `0x3aea4eca` и `0x3ad66358`: циклы, временные коллекции, сохранение промежуточного состояния и вызовы зависимостей. Они сохранены целиком; точные изменения дерева и матриц ещё не объяснены. Evidence `ev_59b2f20231c187216c63ff440595853bb9313a78d9336a7551cc630da672f7e9`, `ev_617e224bd9de8220a1ae83192146fc8a79370c14a251e4af1ec9ff9ef8054427`.

## Ограничения и следующий шаг

1. Стандартный автоанализ **не создал записи функций** для части декодированных методов. Например, Align vtable `+4 -> 0x3af50310` и Distribute `+4 -> 0x3ad651c4`: `inspect_native_instruction` подтверждает `PUSH 0x18`/`PUSH 0x10` и входящие DATA-ссылки из таблиц, но `procedure:null`. `analyze_function` честно вернул `not_found`; полный алгоритм выполнения этих методов не восстановлен. Это не таймаут и не отсутствие кода. Windows Ghidra P0 не допускает нужных мутаций базы для ручного создания функций через текущий REA-контракт.
2. В журнале Ghidra были ошибки разметки нескольких TryBlockMapEntry, overlap function-body repair и GIF-кандидата. Завершённый overview не означает отсутствие этих локальных проблем анализа. Они сохранены в диагностике неуспешных запросов.
3. Rotate, Flip, Crop, Regroup и connector представлены строками и отдельными вспомогательными связями; их полный путь от UI до изменения геометрии не восстановлен. `CropPictureInfoCommand` привязан к lazy type-registration getter `0x3b21062d`, а не доказанному обработчику обрезки.
4. OART не является описанием координат Ribbon. Для сохранения привычных мест кнопок нужны ресурсы/сценарии PowerPoint и отдельная проверка фактического UI. Здесь нет доказательства точного расположения кнопок или динамических вкладок.
5. Экспортные ordinal сопоставления из `research/ppcore-complete/dependency-bindings.json` устанавливают связи файлов; это не поведение и не наблюдённый выбор Windows loader. Большинство экспортов OART безымянные.
6. Для AI Presentation Free эти данные обосновывают раздельные операции и состояния Align/Distribute/Group/Ungroup, осмысленные пороги и дальнейший список проверок. Они не доказывают математическую идентичность реализации. Исходники/декомпиляция Office в код продукта не переносились в этой исследовательской задаче.

Следующий полезный проход: воспроизвести выделения 0/1/2/3 объектов и разные области выравнивания в реальном UI; затем связать результат с указанными слотами и уточнить защитные флаги. Для отсутствующих function records возможен отдельный импорт с явно заданными стартовыми seeds, как в последующем PPCORE-проходе; здесь он не выполнялся. Он должен иметь отдельный профиль и указывать аналитическое происхождение seeds. Изменение текущей Windows P0 базы через API по-прежнему недоступно; повтор того же автоанализа с увеличенным таймаутом сам по себе не решает этот пробел.
