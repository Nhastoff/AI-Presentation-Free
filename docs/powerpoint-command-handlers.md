# Обработчики команд PPCORE: отдельный целевой проход

Объект исследования: установленный PowerPoint Office12 Windows x86, `PPCORE.DLL`, SHA-256 `41ac194cf36becccd0fe64343377be5932060317ad9b83cdbeea77a06de284b5`. Статический анализ REA + Ghidra; выполнение PowerPoint в этом проходе не наблюдалось. Адреса относятся только к этой сборке.

## Граница доказательств

Наличие строки типа `AlignInfoCommand` само по себе не доказывает обработку кнопки «Выровнять». Для установления маршрута нужны ссылки из кода, проверка типа, ветви и вызовы; для полного сопоставления интерфейса дополнительно требуется идентификатор команды в регистрации Ribbon. Имена `FUN_*` не являются исходными именами. Псевдокод Ghidra — восстановленное представление, не исходный код Microsoft; он хранится только как материал исследования и не переносится в AI Presentation Free.

Используется одна непрерывная MCP-сессия, память Ghidra 2 ГБ, стартовый таймаут 30 минут. Наборы Evidence сохраняются после каждого пакета запросов, полный snapshot — при закрытии. Сценарий: `scripts/research-ppcore-commands.cjs`.

## Подтверждённая регистрация Ribbon

`FUN_3010c261`, Evidence `ev_691b4e93da3b751aee5570e24c7370f36dbafd3143cd6b8c0109bf2429e378d2`, содержит следующие наблюдаемые инструкции:

- `0x3010c398`: передача адреса `PowerPoint.ribbonpp`;
- `0x3010c39d`: передача числа `0x1f00`;
- `0x3010c3ab`: косвенный вызов через IAT `0x307ba214`, сопоставленный с `MSO.dll` ordinal 7502;
- после проверки возвращённого `AL` и ненулевого указателя — вызов через IAT `0x307ba210`, ordinal 8146, в `0x3010c3c5`.

Это связывает буквальное имя Ribbon с конкретными импортами MSO. Значение `0x1f00` не объявляется идентификатором кнопки. Данная процедура не раскрывает таблицу всех кнопок, их координаты или точную семантику безымянных экспортов MSO. В этой же процедуре наблюдается чтение `ToolbarConfigSaved` и работа с интерфейсами через виртуальные вызовы; это дополнительное основание считать её частью загрузки/восстановления интерфейса, а не обработчиком отдельной кнопки.

## Выявленный пробел стандартного автоанализа

Область после `0x30154814` содержит байты, соответствующие прологу функции и последовательным проверкам Art-команд, но стандартный автоанализ не включил её в процедуры. Это проверено отдельными `resolve_containing_procedure` (`ev_75c2061dfb25d138216ea77b89fae106c6551e040aca75677a0c762f13fd143c`, `ev_2fe3cde0c2e8b03c623622c08dd90fea70a810adb3873edae034ef156f7a25d3`) и `inspect_native_instruction` (`ev_ac427993a894b64bd635ea5a315bcfe5d49166716cdb20249a4a4b6e48cde17e`: `undecodable`).

Чтение 96 байт с `0x30154814` успешно: `ev_50ab21c7a9526ee0b12ff4fbdbd27df28a69ebfc04a30763443b6ce5cf157fd9`. Начало соответствует `PUSH 0x118; MOV EAX, 0x306d1719; CALL 0x30107d13` — первоначально ручная интерпретация байтов, затем подтверждённая seeded-декомпиляцией. Отрицательный результат xrefs в этой области не доказывает отсутствие использования команд.

Для проверки выполнен отдельный проход с **единственным явно заданным аналитиком адресом функции** `0x30154814`. Файл `research/ppcore-commands/seeds.tsv` не содержит придуманных семантических имён. Профиль и результаты отделены в `research/ppcore-commands/seeded`; исходная DLL не изменяется. Результаты такой декомпиляции рассматриваются с указанием происхождения seed, а не как полностью автоматическое открытие.

### Какие проверки состояния действительно восстановлены

Общий guard `0x3010cc8e`, Evidence `ev_550b63b315d8111604df2098fcffdd9403b03740e040fc963ce09e2b071fb1d7`, возвращает 0 только если внутренний указатель ненулевой, целое поле по смещению `+4` не меньше 1 и поле-указатель по смещению `+0xc` ненулевое. Иначе он возвращает 1, и ветки Align/Distribute/Group уходят в очистку без создания объекта. Именовать эти поля «выбранные фигуры», «заблокированный слой» или «редактирование текста» оснований пока нет.

`0x3011c86d`, Evidence `ev_edc5a4cfc76a08195bbeec1f5e31a84058ebbd80ff8ddfff28253e901af61dc3`, проверяет те же поля и при успехе возвращает адрес внутреннего объекта `+4`, иначе 0. В Regroup проверяется ненулевой результат. Dossier `0x3011c91d` превысил ограничение транспорта; полный результат извлечён из сохранённого bundle по Evidence `ev_713b73d3b022fb9d8366ccd7cb6c4003d00a2bd564b40328a6e57ca9eeaa158b`. Он проверяет те же поля и в неуспешной ветке вызывает MSO ordinal 6848 с `0x38693233, 0`, затем `0x302933a4`. Назначение этого аварийного/диагностического пути — только предположение; имена внутренних полей и пригодная для исходного языка сигнатура возврата не восстановлены.

Для Align и Distribute результат ordinal 3142/3143 инвертируется в байтовый флаг, а при нулевом исходном результате дополнительно формируется контекст через `0x3012e634` и OART ordinal 1927. Называть этот флаг переключателем «относительно слайда» до анализа соответствующих OART-функций нельзя. Общая предварительная ветка функции проверяет контекст и `0x3010ae5a`; её прикладная семантика тоже остаётся неизвестной.

## Сохранение и ограничения

Оба прохода штатно завершены, принадлежащие им процессы и временные Ghidra-базы закрыты. Первый сохранён в `research/ppcore-commands/evidence-bundle.json` и `analysis-snapshot.json`: 30 записей Evidence, восемь dossiers функций, отдельные ссылки, байты и отрицательные результаты разрешения адресов.
